# 未決の設定と既知の穴

この基盤は1コンペも回さずに作った。
下の数値はすべて**当て推量**で、実データで検証していない。
1コンペ回したら、ここを見て調整する。

「たぶん大丈夫」で放置すると、誤検知に苛立って抜け道を常用するようになるか、
逆に緩すぎて何も止まらなくなる。どちらもこの基盤が死ぬ経路。

---

## 調整が要る数値

### 語彙規則の誤検知率

`tools/expkit/defaults/lint.yaml` の146パターン。

攻めた設定にしてある。特に次は正当な用法とぶつかる見込みがある。

| パターン | ぶつかりそうな正当な用法 |
|---|---|
| `効いて` / `効いた` | Kaggle 日本語で常用される。意図的に禁止したが、頻度が高すぎるかもしれない |
| `相性` | 「モデルとデータの相性」は比喩だが、定着した用語でもある |
| `十分` / `妥当` | 「十分統計量」「妥当性検証」など複合語で誤爆する |
| `一定の` | 「一定の間隔で」は量的ぼかしではない |

**判断材料**: 1コンペで `lint_waived` を使った回数と、その理由。
同じ規則を3回以上 waive したなら、その規則は誤検知している。
`lint.yaml` でその規則の `patterns` を絞る。

waive の理由が毎回「表現を変えるのが面倒」なら、規則ではなく使い方の問題。

### `policy.landscape_min_sources` = 5 / `landscape_min_kinds` = 2 / `landscape_min_transferred` = 3

地固めに要る量。

- **多すぎる兆候**: 先例の少ない問題で、5件集めるために関係の薄い出典を
  水増しする。`takeaway` が「一般的に良い手法」ばかりになる
- **少なすぎる兆候**: 地固めを通過したのに、序盤の実験が全部 `priors/` 由来

**判断材料**: `landscape.yaml` の出典のうち、実際に在庫に移して
hit になったものの割合。1件も hit にならないなら、集め方が的外れ。

先例の少ない問題では下限に届かないことがある。その場合は
`why_hard` に「先例が少ない」と書き足し、下限を下げて `moonshot` の
比率を上げる方が正しい。

### `policy.domain_min_facts` = 5 / `domain_min_confirmed` = 2

ドメイン知識の下限。

- **多すぎる兆候**: 事実を5件にするために当たり前のことを書き足す。
  `implication` が「特徴量に使えるかもしれない」ばかりになる
- **少なすぎる兆候**: `error_analysis` で毎回新しい構造が見つかる。
  序盤に見ておけたはずのものを見落としている

### `policy.inconclusive_streak_limit` = 3

判定できない決定がこれだけ続いたら、次の実験に `error_analysis` を強制する。

3 に根拠はない。短すぎると誤り分析ばかりになり、長すぎると手詰まりに
気づくのが遅れる。**判断材料**: 強制された誤り分析が実際に新しい
ドメインの事実を生んだかどうか。生まないなら、そもそも OOF の切り方が悪い。

### `policy.backlog_min_open` = 8

在庫の下限。

- **多すぎる兆候**: 実験を1本立てるたびに補充作業が発生して、実験が止まる
- **少なすぎる兆候**: 終盤に在庫が枯れて、打ち切りゲートが形骸化する

**判断材料**: 1コンペ通して、在庫が下限に張り付いた期間の長さ。
常に張り付いているなら多すぎる。一度も下限に触れなかったなら少なすぎる可能性がある。

### `policy.backlog_min_axes` = 3

在庫が散っているべき軸の数。コンペによっては軸が本質的に少ない
（例: 提供データが1テーブルだけで external_data も pseudo_labeling も使えない）。
その場合は `coverage.yaml` から軸を消し、この値も下げる。

### phase ごとの `tier_quota`

`competition.yaml` の既定値。

```
p0_survey    exploit 0.2 / explore 0.7 / moonshot 0.1
p1_saturate  exploit 0.7 / explore 0.3 / moonshot 0.0
p2_ideas     exploit 0.3 / explore 0.5 / moonshot 0.2
```

**判断材料**: tier ゲートに止められた回数と、そのとき実際に立てた実験の質。
止められて立てた explore が毎回 inconclusive なら、その phase では
explore の比率が高すぎる。

### `policy.hit_rate_ceiling` = 0.8

的中率がこれを超えたら「賭けていない」と警告する。

根拠のある数字ではない。探索と活用のバランスの目安として置いた。
1コンペ分の較正データが溜まったら、実際の分布を見て決め直す。

### 飽和の判定基準

`expctl saturate --criterion` に書く文字列。機械では検証していない。
**探索を始める前に決める**という運用だけがルール。

典型例: 「直近30試行で best がノイズ幅を超えて更新されない」

**判断材料**: 飽和を宣言したあとに、その軸で大きな改善が見つかったかどうか。
見つかったなら基準が緩すぎた。

### `lb_noise`

`competition.yaml`。既定 0。**0 のままだと LB のノイズ判定が効かない。**

見積もり方は2つ。

1. 同一予測を2回提出して差を測る（提出回数を1回消費する）
2. Public のサンプル数から標準誤差を計算する

`/init-competition` が最初の在庫に 1 を入れる。

## 既知の穴

### セッションを普通に閉じたときは検知できない

`PreCompact` hook は compact を捕まえる。しかし**ターミナルを閉じる・放置する
経路には hook が無い**（`SessionEnd` はブロックできない）。

進行中の実験の `notes` が空のままセッションが死ぬと、
どこまで進んでいたかが失われる。

**運用での対処**: `notes` を終わるときではなく、**長い実行を始めるときに書く**。
`expctl new` は実験を回す前に record を作るので、そのタイミングで
「これから40分回す」と書いておけば途中で何が起きても拾える。

**塞ぐなら**: `Stop` hook（エージェントの応答終了ごとに発火）で、
進行中の実験に notes が無いときだけ促す。発火頻度が高いので、
条件を絞らないと雑音になる。

### フレームワーク自身の開発には引き継ぎが効かない

SessionStart hook は `competition.yaml` の `name` が `TODO` のとき黙る
（未初期化のリポジトリで引き継ぎを出しても意味がないため）。
その結果、**このリポジトリ自体を開発するセッションには引き継ぎが無い**。

このファイルがその代わり。フレームワークを触るときは、
未決の判断をここに書き足してからセッションを閉じる。

### 摩擦の記録が端末ごとに分かれる

`.expkit/events.jsonl` は `.gitignore` で除外してある。実験の記録と混ぜたくない
ためだが、その結果 `expctl feedback` は**その端末で起きた摩擦しか集計しない**。

複数の端末でコンペを回すと、ゲートが止めた回数が実際より少なく見える。
waive と `gates_forced` は記録に入るので、そちらは全部集まる。

**塞ぐなら**: `.expkit/events.jsonl` をコミット対象にする。ただし実験と無関係の行が
git の履歴に混ざる。1コンペ回して、端末をまたぐ頻度を見てから決める。

### 出典の捏造を完全には防げない

`landscape.yaml` は URL を必須にし、`expctl landscape check` で
到達性を確かめられる。しかし**到達する URL と、そこに書いてある内容が
`takeaway` と一致していること**は機械で確かめられない。

実在するが読んでいない論文を引き、それらしい `takeaway` を書くことは可能。
`evidence` の仕組み全体がこの前提の上に立っているので、ここは弱点。

**塞ぐなら**: `takeaway` に出典からの短い引用を必須にする。
引用も捏造できるが、人が検証するコストは下がる。1コンペ回してから判断する。

### `expctl status` の出力を LLM が要約する経路を塞げていない

規範（`/decide-next`）で「要約させない」と書いてあるだけで、機械的な強制は無い。
コンテキストが厳しくなったエージェントは要約したがる。

**塞ぐなら**: `status` の出力にハッシュを付け、決定の `rationale` に
そのハッシュを要求する。ただし手続きが重くなる。1コンペ回してから判断する。

## 意図的にやっていないこと

- **phase の自動遷移** — `current_phase` は手で書き換える。
  遷移条件（`exit`）は文章で書いてあり、機械判定していない。
  判定を機械化すると、条件を満たすためだけの実験が生まれる懸念がある。
- **`record.notes` の消去強制** — 実験が終わっても notes は残る。
  害が無いので放置している。
- **提出物の管理** — `submissions/` は `.gitignore` で除外するだけ。
  どの実験がどの提出に対応するかは `metrics.lb` で追える。
