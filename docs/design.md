# 設計

なぜこの形なのか。README は使い方を書く場所なので、理由はここに置く。

## 何を解こうとしているか

エージェントにコンペを回させると、4種類の壊れ方をする。

### 記録が太る

エージェントは自由記述欄を埋めようとする。埋める材料が観測値しかないとき、
水増しの手段は比喩とヘッジしかない。`AUC +0.003` が「わずかながら改善の兆しが
見られる」になる。

問題はここからで、その記述が次のセッションの入力になる。二段目は
「改善の兆し」を事実として受け取る。`+0.003` はもう消えている。三段目では
「改善傾向が確認されている」になる。**情報は単調に減り、文字数は単調に増える。**
最終レポートが意味不明になるのは必然。

### 調べずに手を動かす

汎用の打ち手を汎用の順序で試すだけの進行になる。それは誰がやっても
同じ結果にしかならない。上位との差は、コンペ固有の知識でしか作れない。

### 探索が縮む

- 弱い根拠で打ち切る。ローカルが採点を再現できているか確かめないまま、
  ローカルを当てにする
- Public が上がらないと消極的になる。ノイズを結論と読み替える
- 既存の勝ち筋の微修正ばかり続く。探索の配分を誰も管理していない
- 数値が動かなくなっても闇雲に次を撃つ。手詰まりに気づく機構がない

### セッションが切れない

実験ごとに切ろうとしても、切ると運用状態（回し方、所要時間、どこまで進んだか）
が失われるので続けてしまう。コンテキストが埋まり、`/compact` を打って台無しになる。

## 設計の前提

**文体指導はしない。** 「簡潔に書け」は守られない。規範を書いただけでは、
長い会話の後半で必ず崩れる。

代わりに、**解釈を書ける場所を物理的に減らし、書いた解釈に検証義務を負わせ、
それを機械で強制する。** 守れたかどうかを人間の善意に任せない。

## 記録が太るのを止める

| 仕組み | 中身 |
|---|---|
| 数値と記述の分離 | `metrics.json` は機械しか書かない。sha256 で守り、手で編集すると lint が落ちる |
| 数値への接地 | 記述欄に裸の数値を書けない。`${metrics.cv.mean}` で参照する |
| 字数上限 | `observation` 300字 / `change` 200字。比喩を書く余白を物理的に奪う |
| 禁止語彙 | ヘッジ・比喩・擬人化・評価語・空句・曖昧な量的表現を146パターンで検出 |
| **反証条件の必須化** | `hypothesis` には `falsification` が必須 |
| レポートの機械生成 | 本文は records から組み立て。人が書けるのは600字の結論だけ |

数値への接地には副次効果がある。参照にすると転記ミスと誇張が同時に消える。
手で数字を写す機会がなければ、写し間違いも盛り方もできない。

**反証条件の必須化が核。** 理由は二つ。

第一に、**反証条件を書こうとすると比喩では書けない。**
「モデルが特徴を捉えきれていない」は反証条件が書けないので、そこで自壊する。
書けない考えは記録に入れずに消す、というのが正しい対処になる。

第二に、**反証条件がそのまま次の実験になる。**
次の一手がエージェントの作文ではなく、記録から導かれる。

## 調べる前に手を動かさせない

同梱の `knowledge/priors/` は汎用の記憶から書いた打ち手で、どのコンペでも
同じ内容になる。**汎用の在庫からは汎用のアイデアしか出ない。**

だから最初の phase を `p0_recon`（地固め）にし、2本立てにした。

| | `knowledge/landscape.yaml` | `knowledge/domain.yaml` |
|---|---|---|
| 問い | **何をやればいいか**（手法） | **何が本当か**（対象そのもの） |
| 中身 | 問題の定式化、過去の上位解法、論文 | データの成り立ち、現象の性質、ありえない値 |
| 埋める | `/survey` | `/learn-domain` |
| 終わるか | 序盤で一区切り | **終わらない。誤り分析で増え続ける** |

ドメイン知識をフェーズではなく台帳にしたのは、**調べ終わらない**種類の知識だから。
一度埋めて終わりの成果物にすると腐る。誤り分析の出力がここに流れ込む。

`confidence`（`confirmed` / `likely` / `assumed`）を型で分けるのが肝。
**検証していない仮定が前提として使われるのが「弱い根拠で打ち切る」の正体**なので、
そこを見えるようにする。`assumed` が残っている間は打ち切りが通らない。

出典の捏造対策として URL を必須にし、`expctl landscape check` で到達性を
確かめられるようにした。ただしこれには限界がある（後述）。

## 探索が縮むのを止める

| 仕組み | 中身 |
|---|---|
| 指標実装の検証 | `metric.verified` が false の間、他の軸に進めず打ち切れない |
| CV 信頼性の台帳 | CV-LB の順位相関を集計。`calibrated` になるまで CV を根拠に打ち切れない |
| ノイズ幅の強制 | 差が `lb_noise` 未満なら `miss` ではなく `inconclusive` |
| 探索の網羅マップ | 13軸。未着手の軸が残る限り「打ち手がない」と書けない |
| アイデア在庫 | 未実行が下限を割ると次に進めない |
| tier クォータ | `exploit`/`explore`/`moonshot` の比率を phase ごとに強制 |
| **飽和判定** | 試し尽くした軸への `exploit` を禁止 |
| **誤り分析の強制** | 決定が3回連続で `inconclusive` なら次は `error_analysis` 軸 |
| 較正の追跡 | 期待と実際を突き合わせ、的中率が高すぎると警告 |

### 飽和判定を両刃にした理由

「まずハイパラなど可動域を試し尽くしてから、アイデアを試せる立場に立つ」
という順序は正しい。チューニングされていないベースラインとの比較は交絡するので、
新しいアイデアの上げ幅がチューニング不足の埋め合わせなのか区別できない。

ただし「試し尽くす」に終点がないと、それ自体が**安全で生産的に見える無限の作業**
になる。チューニングは永遠にできて、しかも進んでいる感じがする。

だから飽和は両刃にした。**飽和前は打ち切れず、飽和後は触れない。**
終点を過ぎたら手を出せないので、アイデアに移らざるを得なくなる。

### 的中率が高すぎることを警告する理由

決定の的中率が9割なら、当たる決定しか立てていない。それは賭けていないという意味で、
探索不足の証拠になる。期待値を低く見積もって的中率を上げる抜け道は、
「実際/期待」の比が systematically 大きくなることで露見する。

### 誤り分析を強制する理由

数値が動かないのに闇雲に次を撃つのは、探索ではなく手詰まりの症状。
`inconclusive` が続いている状態で次の実験を撃っても、また判定できない。

そこで OOF 予測を見に行かせる。誤差が集中している切り口を探し、
分かったことを `domain.yaml` に入れる。そこで見つかる着想が、
在庫にある汎用の打ち手より当たる。

### 在庫を数だけで満たせないようにする

在庫の下限は「打ち手がない」と言わせないための仕組みなので、
中身の薄い項目を8件並べて満たされると形骸化する。3点を機械で見る。

| 規則 | 中身 |
|---|---|
| `idea.action_too_vague` | `action` が20字未満は1実験の粒度になっていない |
| `idea.evidence_without_source` | `evidence` が出典を指すこと |
| `backlog.too_narrow` | 在庫が3軸以上に散っていること |

歯止めの本体は**出典要求**。8件を思いつきで埋めるには8個の実在する出典が要る。

そして**ゲートが数えるのは検証を通った項目だけ**。逆向きの穴も塞いである
（中身の無い在庫を口実に打ち切りを止め続けることもできない）。

## セッションが切れないのを止める

**切れないのは規律の問題ではない。切ると本当に何かが失われるから切れない。**
だから対策は「切る規律を持つ」ではなく、**切っても何も失われない状態にする**こと。

| 仕組み | 中身 |
|---|---|
| `expctl brief` | 進行中の実験・いま取れる手・未決着の決定・運用状態を記録から生成 |
| SessionStart hook | 引き継ぎを自動注入。`startup`/`resume`/`clear`/`compact` すべてで走る |
| `record.notes` | ファイルから復元できない唯一の情報 |
| `knowledge/operations.md` | 回し方・環境の癖・踏んだ失敗 |
| PreCompact hook | compact を止めず、書き出されていない状態を指摘して引き継ぎを保存 |

SessionStart は `source: compact` でも走るので、**compact の直後にファイルから
実データが読み直される**。要約ではなく元の数値が戻るので、compact が致命傷でなくなる。

compact をブロックしないのは意図的。コンテキストが埋まった状態で止めると
逃げ場がなくなる。**止めるのではなく無害にする。**

### セッションの境界が持つ意味

「一実験一セッション」は、普通コンテキスト長で説明される。それは弱い理由で、
コンテキストは伸び続けている。

本当の理由は、この基盤が防ごうとしている失敗そのものにある。
長いセッションでは、エージェントが1時間前に自分で書いた散文がコンテキストに残り、
それを一次資料として読み直す。「さっき集約特徴が効いたので」と、自分の要約を
根拠に次を決める。元の数値はもう遥か上にある。
**解釈の再解釈が、1つのセッションの中で起きている状態。**

セッションの境界は、一次資料に戻ることを強制する装置として機能する。

コンテキストを食うのは実験そのものではなく周辺（データ探索・失敗の原因追跡・
公開解法の読み込み）で、これらは出力が大量で結論は数行。
サブエージェントに投げて結論だけ受け取り、本体は薄く保つ。
記録を書く作業と次の一手を決める作業は委譲しない。規範と判断の責任は本体にある。

## 設計上の緊張

**記録の規範だけを強くすると、探索は縮む。**

根拠を義務化すれば、エージェントは根拠を書けることしかやらなくなる。
根拠が一番書きやすいのは既存の勝ち筋の微修正なので、防御を固めるほど保守化する。

だから4方向に同時に手を打っている。片方だけ入れると悪化する。

同じ理由で、tier クォータは phase 依存にしてある。
`p2_saturate` では exploit 多めが正しく、`p3_ideas` では explore 比率が上がる。
一定の比率を全期間に課すと、可動域を出し切る段階で不要な探索を強いることになる。

## 抜け道の設計

規範に抜け道が無いと、守れない場面で作業が止まる。止まると人は規範ごと外す。
だから抜け道は用意するが、**使ったこと自体が記録に残る**ようにした。

- 語彙規則は `lint_waived` で抜けられる。規則名と20字以上の理由が要る
- ゲートは `--force` で押し切れる。押し切った内容が `record.yaml` の
  `gates_forced` に残る

**抜けられないものは4つ。** 反証条件、改竄検知、スキーマ、参照解決。
ここを緩めると基盤の意味がなくなる。

## この設計の弱点

`docs/open-questions.md` に、当て推量の数値と既知の穴を書いてある。
特に大きいのは次の2つ。

**出典の捏造を完全には防げない。** URL の到達性は確かめられるが、
そこに書いてある内容が `takeaway` と一致することは機械で確かめられない。
`evidence` を要求する仕組み全体がこの前提の上に立っている。

**`expctl status` の出力を要約する経路を塞げていない。**
「要約させない」と規範に書いてあるだけで、機械的な強制がない。
コンテキストが厳しくなったエージェントは要約したがる。
