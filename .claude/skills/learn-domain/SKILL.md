# ドメイン知識を貯める

`knowledge/landscape.yaml` が答えるのは「**何をやればいいか**」（手法の話）。
ここが答えるのは「**何が本当か**」（対象そのものの話）。

ドメイン知識は調べ終わらない。データを見るたび、モデルが外すたびに増える。
だから台帳（`knowledge/domain.yaml`）として持ち、一度埋めて終わりにしない。

供給源は2つあり、どこにいるかで使い分ける。

| いつ | 何を見る | `source` |
|---|---|---|
| モデルを作る前 | データそのもの | `data_observation` |
| モデルを作った後 | モデルの誤り | `error_analysis` |

**地固めの段階ではデータ観察だけで足りる。** モデルが無くても、
`domain_min_confirmed`（既定2件）は実データを見れば確かめられる。

## confidence を必ず分ける

| 値 | 意味 |
|---|---|
| `confirmed` | 自分で確かめた。`evidence` に再確認できる根拠がある |
| `likely` | 出典はあるが、このデータでは確かめていない |
| `assumed` | 仮定。まだ何の裏付けもない |

**検証していない仮定が前提として使われるのが「弱い根拠で打ち切る」の正体。**
だから型で分ける。`assumed` が残っている間は打ち切りの決定が通らない。

`confirmed` を名乗るには、他人が同じ手順で再確認できる `evidence` が要る
（確認に使った実験 `exp0003` / URL / 地固めの出典 `s0001`）。
読んだだけなら `likely`。思っただけなら `assumed`。

## モデルを作る前 — データを見る

順に見る。見つからなかったことも事実として記録する価値がある。

### 1. 単位と粒度

1行は何か。患者か、画像か、取引か。**同じ実体から複数行が出ていないか。**
出ているなら、それが分割戦略を決める。

### 2. 目的変数の分布

不均衡の程度。裾の重さ。ありえない値。ラベルの付け方（誰がいつ付けたか）。
ラベルノイズの見当。

### 3. 欠損の構造

ランダムに欠けているのか、特定の条件で欠けるのか。
**欠損そのものが情報を持つ場合がある**（測っていない＝必要がなかった）。

### 4. 時間と場所

収集期間。train と test の期間が分かれているか。
収集場所（病院・店舗・センサー）が分かれているか。

### 5. ありえない値と物理制約

負にならない量が負になっていないか。単位が混ざっていないか。
合計が一致すべきものが一致しているか。
**ここで見つかる制約は、後処理でそのまま使える。**

### 6. 領域の常識

その分野で当たり前とされていることを調べる。
何が原因で何が結果か。何が測定の代理指標か。

## モデルを作った後 — 誤りを見る

決定が `inconclusive_streak_limit`（既定3回）連続で判定できなくなると、
ゲートが次の実験に `error_analysis` 軸を要求する。
**数値が動かないのに闇雲に次を撃つのは、探索ではなく手詰まりの症状。**

### 1. OOF 予測を用意する

実験スクリプトが out-of-fold 予測を保存していること。
`experiments/<id>/artifacts/oof.npy`（`.gitignore` で除外される）。
保存していないなら、それを直すのが最初の打ち手。

### 2. 誤差を切る

サンプルごとの誤差を出し、軸を変えて集計する。

- fold ごと
- 目的変数の値域ごと（大きい値だけ外していないか）
- グループごと（患者・店舗・期間）
- 特徴量の分位ごと
- メタデータごと（装置、撮影条件、カテゴリ）

**誤差が集中している切り口を探す。** 均等に散っているなら、
そのモデルの限界であって、その軸に打ち手はない。

### 3. 最悪の切り口の実例を見る

集計で終わらせない。誤差が大きい実例を10件くらい実際に見る。
共通点を探す。ここでしか出てこない着想がある。

### 4. 事実として書く

観測は事実、原因は仮説。混ぜない。

```
悪い: モデルは高齢の患者が苦手。
      → 擬人化。何がどれだけかを言っていない。lint が落とす。

良い: statement: 誤差の上位10%のうち72%が、撮影装置Bの画像に集中している。
      source: error_analysis
      evidence: exp0007 の OOF を装置ごとに集計した。手順は
                knowledge/operations.md の「誤差の切り方」に書いた。
      confidence: confirmed
      implication: 装置を特徴量に入れるか、装置ごとに正規化する。
                   test の装置比率が train と違うなら分布ずれの原因でもある。
```

原因の推測を書きたくなったら、それは `record.yaml` の `hypothesis` に
反証条件つきで書く。ドメインの事実ではない。

### 5. 在庫に移す

`implication` を1実験の粒度に割って在庫に入れる。

```
uv run expctl idea add \
  --action "撮影装置IDを特徴量に加え、装置ごとの正規化と比較する。" \
  --axes features --tier explore --magnitude 0.004 \
  --evidence "d0007" --cost 0.6
```

移したら `transferred_to: [i0015]` を書き戻す。

## 確かめる

```
uv run expctl lint domain
```

## 通らないときによくある原因

| 落ちる規則 | 意味 |
|---|---|
| `domain.too_few_facts` | 事実が5件未満。まだ見足りない |
| `domain.nothing_confirmed` | 読んだだけの知識しかない。実データで確かめられることを確かめる |
| `domain.unconfirmable_evidence` | `confirmed` なのに再確認できる根拠がない。`likely` に落とす |
| `domain.implication_too_thin` | 打ち手にどう効くかが書けていない。雑学は台帳に置かない |
| `vocab.metaphor` | 「苦手」「捉えられていない」。何がどれだけかを書く |

## assumed を放置しない

`assumed` は書いてよい。ただし**残したまま打ち切れない。**
仮定の上に実験を積んでいることが見えるようにするための型なので、
確かめて `confirmed` にするか、誤りと分かったら消す。

`expctl status` に未検証の仮定の件数が出る。
