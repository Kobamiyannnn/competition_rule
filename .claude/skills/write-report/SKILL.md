# レポートを作る

レポートは著作物ではなく生成物として扱う。
本文は `expctl report` が records と metrics から機械的に組み立てる。
**自由に書ける面積を与えなければ、太った表現は入りようがない。**

## 順序

### 1. 記録が揃っているか確かめる

```
tools/expctl lint
```

全件が ok になってから作る。落ちている記録があるまま作ると、
規範を通っていない文がそのままレポートに載る。

### 2. 結論を書く

`reports/conclusion.md` に **600字以内**で書く。
これがレポート中で人と LLM が自由に書ける唯一の場所で、
`record.observation` と同じ strict プロファイルの lint がかかる。
特定の実験に紐づかないので `${...}` 参照は使えず、数値はそのまま書いてよい。
禁じられるのは語彙の方 —「効いた」「大幅に」「と思われる」は通らない。

書く内容は3つに限る。

1. **最終的に何を提出したか** — 構成を事実として
2. **効いたことと効かなかったこと** — metrics の数値で
3. **未決着で残ったこと** — 未検証の仮説と未着手の軸

書かないもの。

- 「今後の課題」「さらなる検証が必要」— 未決着の欄が機械で出るので重複
- 「全体として」「総合的に判断すると」— 空句
- 実験一覧の言い換え — 表が下にある

```
悪い: 今回のコンペでは、特徴量エンジニアリングが全体として重要であることが
      示唆された。特にユーザ単位の集約が有効に機能し、大幅なスコア向上に
      つながった。今後はさらなる検証が求められる。

良い: 提出は LightGBM と CatBoost の等重量平均。cv.mean 0.8901、
      LB 0.8874。cv.mean を最も動かしたのはユーザ単位の集約特徴
      （exp0004、+0.0043）と閾値最適化（exp0011、+0.0021）。
      疑似ラベルは3回試していずれもノイズ幅未満で判定できていない（dec0008）。
      外部データと ensemble の重み最適化は未着手のまま締切を迎えた。
```

悪い方は5文で、数値がひとつもない。良い方は同じ長さで、
何を提出したか・何がどれだけ効いたか・何が残ったかが全部入っている。

### 3. 生成する

```
tools/expctl report
```

`reports/report.md` ができる。結論の欄が lint に落ちていれば
終了コードが 1 になり、指摘が出る。直してから配る。

## レポートに載るもの

すべて記録から機械的に組み立てられる。手で書く欄はない。

| 節 | 出典 |
|---|---|
| コンペ | `competition.yaml` |
| 検証の信頼性 | CV-LB のペアと順位相関 |
| 実験 | `record.yaml` + `metrics.json` |
| 探索の網羅 | `knowledge/coverage.yaml` |
| 意思決定の台帳 | `decisions/*.yaml` と較正 |
| 仮説 | 各 record の `hypothesis` |
| 未実行のアイデア在庫 | `ideas/backlog.yaml` |
| 探索の姿勢に対する指摘 | 較正と tier 配分から自動検出 |

**`reports/report.md` を手で編集しない。** 次の生成で消える。
直したいなら、元になっている records / metrics / conclusion.md を直す。

## 内容が薄いと感じたとき

レポートが薄いのは書き方の問題ではなく、記録が薄いという事実の表示。
文章を足して埋めない。足りていないのは次のどれか。

- `hypothesis` が全部空 → 反証可能な仮説を立てずに進めてきた
- 決定が `inconclusive` ばかり → ノイズ幅に対して実験の分解能が足りない
- 未着手の軸が多い → 探索が狭い

これらは記録の欠損ではなく、進め方の結果。レポートにそう出るのが正しい。
