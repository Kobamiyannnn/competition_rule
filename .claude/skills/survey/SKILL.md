# 地固め

`knowledge/priors/` は汎用の打ち手で、どのコンペでも同じ内容になる。
**汎用の在庫からは汎用のアイデアしか出ない。**
ここでやるのは、このコンペ固有の外部知識を集めて在庫の種にすること。

これが済むまで、`metric_fidelity` / `validation` / `data_leak` 以外の軸には
ゲートで進めない。調べる前に手を動かすと、汎用の打ち手を汎用の順序で
試すだけになり、上位との差は最後まで埋まらない。

## 順序

### 1. コンペ自身の資料を読む

先に外を探さない。まず手元を読む。

- データの説明ページ（列の意味、収集方法、既知の欠陥）
- 評価ページ（指標の正確な定義）
- ルール（外部データの可否、提出形式、計算資源の制限）
- ディスカッション（すでに誰かが見つけていることは、探す必要がない）

### 2. 問題を既知の定式化に落とす

`knowledge/landscape.yaml` の `task` を埋める。**ここが調査の成否を決める。**

```yaml
task:
  statement: 患者の検査画像から、3か月後の再発の有無を予測する。
  formulation: 不均衡二値分類。患者単位のグループ構造あり、ラベルは追跡打ち切りを含む。
  why_hard: 陽性が2%。同一患者から複数枚あり、患者をまたぐ分割をしないとリークする。
```

- `statement` はデータではなく**問題**を書く
- `formulation` は**既知の問題設定の名前**で書く。ここが「予測する」のような
  一般語だと検索できない。「順序回帰」「metric learning」「打ち切りを含む生存時間解析」
  のように、論文が使う語彙に翻訳する
- `why_hard` が空だと調査の的が定まらず、「一般的に良い手法」を集めただけの
  役に立たない landscape になる

### 3. 調べる

`formulation` と `why_hard` を検索語にする。順序は効率順。

| 順 | 何を | 探し方 | kind |
|---|---|---|---|
| 1 | 過去の類似コンペの上位解法 | `kaggle <formulation> 1st place solution`、似た指標・似たデータ形式のコンペ | `solution` |
| 2 | このコンペのディスカッション | すでに共有されている知見 | `discussion` |
| 3 | 定式化そのものの論文 | arXiv / Papers with Code。`why_hard` の語を足す | `paper` |
| 4 | 近いベンチマークの SOTA | この問題が既知のベンチマークに近いなら、その上位手法が事前分布 | `benchmark` |
| 5 | データの公式説明・元論文 | データの作られ方が分かるとリークと分布ずれの見当がつく | `dataset_doc` |
| 6 | 実装記事 | 実装の落とし穴 | `blog` |

**1 と 2 を先にやる。** 論文より効率がいい。上位解法は「このタスクで実際に
効いたこと」がそのまま書いてあり、論文は「一般に効くこと」しか書いていない。

### 4. 記録する

出典ごとに `sources` に追加する。

```yaml
- id: s0003
  kind: solution
  title: "RSNA 2023 1st place solution"
  url: https://www.kaggle.com/competitions/.../discussion/...
  year: 2023
  accessed_at: 2026-09-07
  relevance: |
    同じ患者単位のグループ構造と、同程度の陽性割合を持つ。
  takeaway: |
    患者単位の StratifiedGroupKFold で切り、陽性を含む患者を層化に使う。
    画像単位で切ると CV が 0.05 楽観的になると報告している。
  transferred_to: []
```

書き方の規則。

- **実際に開いた URL だけを書く。** 検索結果に出ただけで開けなかったものは
  記録しない。出典が捏造されると `evidence` の仕組み全体が意味を失う
- `takeaway` は**移せる打ち手**を書く。「良い結果を報告している」は移せない。
  何をどうするのかまで書く（30字以上）
- **`knowledge/priors/` にすでにあることは書かない。**
  「GBDT を使う」「アンサンブルする」は汎用の打ち手で、landscape の意味がない。
  ここに書くのは、このコンペ固有の情報だけ
- 種類を偏らせない。論文だけでは実装の勘所が分からず、
  解法だけでは原理が分からない（下限2種類）

### 5. 在庫に移す

調べただけでは打ち手にならない。`takeaway` を1実験の粒度に割って在庫に入れる。

```
uv run expctl idea add \
  --action "患者単位の StratifiedGroupKFold に切り替え、画像単位分割との CV-LB gap を比べる。" \
  --axes validation --tier explore --magnitude 0.01 \
  --evidence "s0003" --cost 0.8
```

移したら `transferred_to: [i0004]` を書き戻す。

**takeaway と action は別物。** takeaway は「その出典が何をしたか」、
action は「このコンペで何をするか」。そのまま写すと粒度が合わない。

### 6. 確かめる

```
uv run expctl lint landscape        # スキーマと語彙と量
uv run expctl landscape check       # URL が実在するか
```

両方通ったら地固めは済み。`expctl status` の「地固め」が「済」になり、
modeling 系の軸に進めるようになる。

## 通らないときによくある原因

| 落ちる規則 | 意味 |
|---|---|
| `landscape.too_few_sources` | 出典が5件未満。まだ調べ足りない |
| `landscape.one_kind_only` | 論文だけ、解法だけ。種類を散らす |
| `landscape.not_transferred` | 調べただけで在庫に移していない |
| `landscape.takeaway_too_thin` | 「良い結果」で終わっている。何をどうするのかを書く |
| `landscape.bad_url` | URL の形になっていない。実際に開いたものを貼る |

## 途中でやめない

出典が5件集まらないなら、`formulation` が一般的すぎる可能性が高い。
2 に戻って定式化を書き直す。「分類問題」では何も出てこないが、
「不均衡・グループ構造つき・弱ラベル」まで絞ると探せる。

それでも見つからないなら、それ自体が情報になる。
**先例の少ない問題だと分かったことを `why_hard` に書き足す。**
その場合、`moonshot` の比率を上げる根拠になる。
