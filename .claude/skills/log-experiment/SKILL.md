# 実験記録の書き方

記録は次の実験の入力になる。ここで解釈を混ぜると、次のセッションが
その解釈を事実として受け取る。数値は消え、評価語だけが残る。
それを防ぐのがこの規範。

## 順序

1. 実験スクリプトから `expkit.metrics.write` で `metrics.json` を書く
2. `record.yaml` の記述欄を埋める
3. `uv run expctl lint <exp_id>` を通す
4. 通ったらコミットする

`metrics.json` は**絶対に手で編集しない**。integrity ハッシュがずれて lint が落ちる。
LB スコアだけは `uv run expctl lb <exp_id> --public <score>` で差せる。

## 欄の書き分け

3つの欄は、それぞれ別の問いに答える。混ぜない。

| 欄 | 答える問い | 書いてよいもの |
|---|---|---|
| `change` | **何を変えたか** | 前実験との差分だけ |
| `observation` | **何が起きたか** | 測定値と、測定値から直接読めること |
| `hypothesis` | **なぜだと考えるか** | 解釈。ただし反証条件つき |

### change — 何を変えたか

前実験（`based_on`）との差分だけを書く。良し悪しは書かない。
`diff` に機械可読な形でも書いておくと、レポートが正確になる。

```
悪い: 特徴量を見直して、より効果的な集約を追加した。
良い: ユーザ単位の集約特徴（購入額の mean / std / count）を12列追加した。
      他の設定は変更していない。
```

悪い方は「見直して」が何をしたか言っておらず、「効果的」は結果の話が
混ざっている。change は結果を知る前に書けるはずの内容。

### observation — 何が起きたか

**裸の数値を書かない。** `metrics.json` を `${...}` で参照する。
参照は `${metrics.cv.mean}` のように書き、`metrics.` で始まる参照を
最低1つ含める（`${config...}` は測定値ではないので数に入らない）。

```
悪い: CV が 0.8712 まで大幅に改善した。この特徴量がよく効いている印象。
良い: cv.mean は ${metrics.cv.mean}、fold 間の std は ${metrics.cv.std}。
      fold 別では最小 ${metrics.cv.folds[0]}、最大 ${metrics.cv.folds[3]}。
```

悪い方の問題は3つ。数値を手で写している（転記ミスの余地がある）、
「大幅」がどれだけか言っていない、「効いている印象」が観測ではなく解釈。

観測から直接読めることは書いてよい。
「fold 3 だけが他より低い」は観測。「fold 3 のデータが難しい」は解釈。

### hypothesis — なぜだと考えるか

**空でよい。** 書くなら `falsification` が必須で、書けない考えは
この欄に書かない（要素ごと消す）。

反証条件は「この仮説が偽なら、どの実験で何がどうなるはずか」を、
観測可能な形で書く。条件節（〜なら / 〜の場合）と、
観測可能なもの（閾値・比較・metrics 参照）の両方を含める。

```
悪い: statement: 集約特徴がモデルの表現力を上げた。
      falsification: 効かない場合もある。

良い: statement: 集約の単位がユーザであることが寄与している。行単位の
                 情報だけでは同一ユーザの行の関係を表現できない。
      falsification: 集約の単位をユーザから乱数グループに置き換えて同じ12列を
                     作り、cv.mean が ${metrics.cv.std} を超えて下がらないなら、
                     この仮説は誤り。
```

悪い方の反証条件は、どんな結果とも両立するので何も禁じていない。
良い方は具体的な次の実験を指定していて、結果が仮説を殺しうる。

**反証条件が書けないなら、それは仮説ではなく感想。** 消す。
消すのは負けではない。未検証の感想を残す方が、あとで前提にされて害になる。

## 書けないときの対処

反証条件が書けない考えが浮かんだときの選択肢は3つ。

1. **消す。** 最も多い正解。
2. **観測に降ろす。** 「モデルが〇〇を理解していない」→ 実際に見た数値は何か。
   「fold 3 の cv が他より ${...} 低い」なら観測として書ける。
3. **仮説を割る。** 大きすぎて反証できないなら、反証できる粒度まで割る。

## 抜け道

語彙規則だけは `lint_waived` で抜けられる。規則名と20字以上の理由が要る。

```yaml
lint_waived:
  - rule: vocab.metaphor
    reason: |
      「相性」はこのコンペの公式ドキュメントで使われている用語で、
      比喩ではなく定義された概念を指している。
```

反証条件・改竄検知・スキーマ・参照解決は抜けられない。
lint に落ちたときは、抜けるのではなく直すのが既定。

## よく落ちる点

- `${metrics.cv.stdev}` のような存在しない参照 → エラーが実在するキーを教えるので直す
- `hypothesis` に反証条件が無い → 消すか、反証条件を書く
- 「効いた」「大幅に」「と思われる」 → 数値で言い直す
- `axes` が空 → 触った軸を書く。網羅マップが更新されない
- 裸の数値 → `${...}` 参照にする
